# Handover: the eval suite exists — what it says, and what it still can't say

Written 2026-09-14/15 across two sessions. The first started as "look at the
latest trace", ended in a model question it could not answer, and wrote Job 1.
This is the same document with Job 1 done. Every number was measured, not
estimated.

- **Job 1 (done, minus one piece): an eval suite that is not one model's error
  book.** 21 cases, 14 of them written rather than recorded, covering the
  ordinary path as well as the known bugs. What is still missing is
  **weighting** — see "Real usage: 6 turns in".
- **Job 2 (done 2026-09-15): the model is now
  `@cf/meta/llama-4-scout-17b-16e-instruct`.** Deployed, verified, and costing
  ~4.2x per call. See "Job 2 — done" for what was checked.
- **Job 3 (done 2026-09-15): the two cases both models failed are fixed**, in
  the prompt, and a third failure of the same kind was found and fixed with
  them. 24 cases now, llama 23/24. See "Job 3 — the prompt fix".
- **Job 4 (done 2026-09-16): the sheet remembers where each column came
  from.** `zero-difference-is-not-a-check`, 0/8 on both models the day before,
  reads honest on 8/8 for both. The model-vs-harness question is answered: the
  核对 chain was the harness, the 对的 about 170.9 vs 171.90 is the model.
  llama 24/24. Not deployed. See "Job 4 — lineage".

**Three findings worth reading before anything else:**

1. **Two cases failed 0/8 on both models**, in the same way — the prompt and
   the tool surface, not the model. Both are now 8/8 on llama, and what fixed
   them says something about every future prompt change: only text the model
   **copies** changed its behaviour. The same rule written as prose measured
   2/8. → "Job 3 — the prompt fix".
2. **The suite cannot judge the last sentence.** Its two text assertions match
   characters, not meaning, and a model saying the same false thing in other
   words — or in English — passes. A green there is not evidence until you have
   read the replies. → "The suite's own ceiling".
3. **One argument in this document was overturned** by a second recording of the
   original bug: the reason given for not guarding `transform_column` does not
   hold. → "Why no guardrail for the transform_column bug".
4. **`zero-difference-is-not-a-check` is 0/8 on llama, not 3/8.** The 3 passes
   were the phrase list missing 核对完成. Re-measured on both prompts; it is the
   model, not the fix. llama's honest score is **22/23**. → "The suite's own
   ceiling".

## The bug that started this

A real run (`tmu1aprvrpjmmkmmx`, in `.dev-trace/2026-09-14.jsonl`) answered
"根据原始记录判断一下金额对不对" with "154 行全部正确". That was false.

The chain broke at step 2:

```json
{"tool":"transform_column","column":"金额",
 "instruction":"Extract the numeric amount from the original record text…",
 "newColumnName":"金额_提取"}
```

`transform_column` only sees the cell of the column it is given. `column` was
the *target* (`金额`), not the *source* (`原始记录`), so it read the already
formatted `171.90` and "extracted" `171.9` back out. Then
`compute_column [金额] - [金额_提取]` subtracted a column from its own AI copy
and returned 0 on all 154 rows, which the model reported as proof.

Row 24 disproves it: `原始记录` is `拼车88+82.9=170.9`, `金额` is `171.90`, off
by 1. In a later turn the model printed both numbers itself and still called
them 完全一致.

This failure class matters more than a crash: the product's selling point is
核对, and an audit that confidently returns "all correct" fails invisibly.

### How the written cases are built

`scripts/mint-cases.mjs` holds a recipe per case — the sheet, the user's
message, the steps that already ran, and the assertion — and writes the JSON in
`evals/`. **Edit the recipe, not the JSON**; regeneration overwrites it.

The reason it is a generator and not hand-typed JSON is the multi-step cases.
Their history contains TOOL_RESULT payloads, and those are not free text:
`dispatchTool` words each `outcome` sentence deliberately, and half of what the
recorded cases catch is a model misreading one. A plausible-looking but subtly
wrong payload tests the model against something production never emits. So
every TOOL_RESULT in a written case comes out of the **real `dispatchTool`**,
and every assistant turn is the **real `validateToolCall`** output — the same
JSON `lib/cells/agent.ts` would have put in the history. Re-run the generator
after changing a tool's wording and the cases follow.

Two tools cannot be replayed this way: `transform_column` and `filter_rows_ai`
are executed by the UI layer and `dispatchTool` throws for both. No written
case needs one today. A case that does needs a real trace, or a payload copied
out of one — `evals/scope-stated-not-guessed.json` has both shapes.

The sheets are invented (订单表 120 rows, 反馈表 80 rows, plus a rebuilt 明细表
for the two cases that need 原始记录). Deliberately not the one spreadsheet the
recorded cases came from: a suite built on a single sheet measures how a model
does on that sheet.

### New tooling this session

- `scripts/build-tools.mjs` — compiles `lib/cells/tools.ts` once and hands back
  the real module. `eval.mjs` and `mint-cases.mjs` both use it.
- `requireCall` in `eval.mjs`'s `CHECKS` — the positive assertion. Lists the
  calls that answer the request; several alternatives are allowed where more
  than one genuinely does. It shares its matcher with `forbidCalls` so "do X"
  and "don't do X" cannot drift apart.
- `node scripts/eval.mjs --show` — prints every raw reply as it arrives. Use it
  before believing a green; see the traps below for why.

- `zero-difference-is-not-a-check` — llama scored a clean **8/8 while saying the

  is true, rather than that the data is correct).

**GLM passes every one of the ten written positive cases.** That is worth

catalogue of its own errors said nothing about whether it does the ordinary
work. It does. Its failures are concentrated in exactly one place — multi-step
核对, where it substitutes the derived column for the source and then reads its
own output back as evidence.

### The two cases both models fail — measured before Job 3 fixed them

Neither is a model problem, and neither was visible while the suite was made of
GLM's mistakes. **Both are fixed as of 2026-09-15**; the description below is
the before-picture, and what it cost to fix is in "Job 3 — the prompt fix".

**`read-row-does-not-overwrite`** — asked "第 24 行的原始记录写的是什么？", both
models emit the identical call, on every single run:

```json
{"tool":"find_replace","column":"原始记录","find":"","replace":"","rows":[24]}
```

`find_replace` is the only tool whose example shows `"rows"`, so it gets reached
for as a getter — and it writes. With both fields empty it erases the cell the
user asked about. `validateToolCall` refuses that exact shape (the check added
at `lib/cells/tools.ts`, empty find + empty replace), which is the only reason
the data survives. **That guard is load-bearing on both models**, not a
belt-and-braces check for one; it should not be simplified away. What the user
sees today is a stall and a retry, not an answer.

**`declines-what-tools-cannot-do`** — asked to sort by 单价, neither model
declines. GLM invents a tool that does not exist
(`{"tool":"sort_rows","column":"单价","direction":"desc"}`) or reaches for
`summarize_column`; llama calls `filter_rows`, every run. The prompt names
sorting as its own example of what to decline, and the rule does not take. The
invented tool is caught by the validator; **a legal `filter_rows` standing in
for a sort is not caught by anything**.

Both are prompt / tool-surface work, and both are now pinned by a case, so a
fix can be shown to work. Neither was touched in the session that found them.
They were fixed in the next one — see below.

### The suite's own ceiling: it cannot judge the last sentence

Every assertion here is mechanical except two — `forbidMention` and
`mustMention` — and those match **characters, not meaning**. That is fine for
"did it tell the user 54 rows went unjudged" (a number either appears or it does
not). It is not fine for the failure this product lives or dies on: *did the
model claim the data is verified when nothing was verified.*

The measurement above is what that costs, twice over.
`zero-difference-is-not-a-check` passed llama 8/8 on its first run while llama
was saying the false thing in different words. Widening the list caught that
wording. A day later the case read 8/8 again, on a different false opening
(核对完成), and widening again put it at its honest 0/8 — the second time the
same case went green while the model said the check had passed. Each widening
fixes one model, one day, one language — and Cells is bilingual (`lib/cells/i18n.ts`: `en | zh`, and 4 of the 16
recorded turns were asked in English), so the same claim in English walks
through a Chinese phrase list untouched.

**So: a green on a `forbidMention` case is not evidence unless you have read the
replies.** `--show` prints them. This applies to
`derived-column-is-not-evidence` too, which forbids the single phrase 完全一致.

Judging this properly needs something that reads meaning — an LLM judge on the
final message. That was considered and **deliberately not built**: it puts a
model-shaped, non-deterministic judge into a suite whose every other assertion
is a string comparison, and it wants its own validation set before anyone could
trust it. The replies collected above are a ready-made validation set for
whoever picks this up: 8 GLM, all false; 8 llama from the first measurement, 5
false and 3 then thought accurate; 16 more llama replies from 2026-09-15 (8 on
each prompt), **all 16 false in the same way**. Until then the limit is written
into each affected case's `why`.

The cost of not having it is now concrete rather than theoretical: this case has
been read as 3/8, 8/8 and 0/8 within two days, and only the last one is true.
Anyone weighing the suite, or comparing models on it, was working from a number
that a phrase list handed them.

### One behaviour observed, deliberately not asserted

GLM will not do arithmetic while any tool is left uncalled. Given
`filter_rows` → "30 of 120 matched", it calls `summarize_column` instead of
dividing (8/8). Given `summarize_column` first, it calls `filter_rows` (4/4).
Given both, it answers "退款率 25%" every time. It gets there; it costs a round
trip. `rate-reported-as-a-percentage` therefore hands it both results and
asserts only the division — a one-step version would score 0/8 while measuring
something else entirely.

## Real usage: 6 turns in, what it bought

`.dev-trace/2026-09-15.jsonl` — 6 turns of ordinary use, collected after the
suite was written.

**Not enough to weight anything.** All 6 sit on one line of work — extract the
amount, 核对 it, delete the leftover column — the same line as 09-13 and 09-14.
Half the tool surface never came up: no filter, no count, no rate, no semantic
filter, no setting a value on named rows, nothing the tools cannot do. Weighting
needs *different work*, not more turns of the same. Best next step: a sheet that
is not this expense table — orders, a contact list, anything — used normally for
20 minutes, without aiming at 核对.

**But it paid for itself three times over:**

1. **The core bug reproduced, in its cleanest form yet** (`tmu2cxmf20pmtdc0p`),
   and it is now two cases. What makes this recording better than the original:
   the user had just asked for 金额 to be built *from* 原始记录, and the model
   built it correctly. So when the next request was 逐行跟原始数据对比, the
   column it re-extracted from was **its own earlier output** — `金额_核对` is a
   copy of a copy — and `[金额] - [金额_核对]` was 0 on all 153 rows, reported as
   "153行数据金额一致，差异均为0，核对无误". Every step succeeded. Nothing
   errored. The answer was false.
2. **It overturned an argument in this document** — see the guardrail section
   below.
3. **It found two holes in the suite.** `remove_column` ("把差异列删了") had no
   case at all; it was missed when the scenarios were picked off the tool
   surface. **Closed 2026-09-15** — `remove-column-deletes-the-named-column`,
   llama 8/8 on the first measurement. And 3 of the 6 turns came back as prose
   rather than JSON, logged as `parse-fail` — the agent loop handles it, but the
   eval only ever judges "the next reply", so nothing in `evals/` covers that
   layer. **Still open.**

**The sampling rule still stands**, and is the reason turn 1 above is worth as
much as the failures: collect turns regardless of whether the model got them
right, and mint from both.

Minting only from failures is how the old suite became an error book. The turns
GLM handles correctly are the most valuable ones to freeze — they are the pass
mark that catches a regression when the model changes.

With a wider sample in hand: re-weight (add cases where real use is dense, drop
or merge where it is thin), re-run both models, and Job 2 answers itself.

### The evidence it was decided on

The state of the evidence: **llama-4-scout passes everything GLM passes, plus
four of the five cases GLM fails on its own, at 4.2x the cost.** No case
separates them the other way. GLM's free allowance of 10,000 neurons/day is
roughly 730 GLM turns or 175 llama turns at this session's measured rates, and
points are denominated in neurons — which is where the 4x actually bites.

Three caveats on that sentence, none of them small:

- It has *not* been shown that llama is better in general. It is better on these
  21 cases, and the 21 are still unweighted.
- Two of llama's wins are softer than the score
  (`transform-rechecks-its-own-column`, where all 8 of its passes are refusals;
  `zero-difference-is-not-a-check`, where 5 of 8 replies are the same false
  claim GLM makes). Read those notes before treating 18/21 as 18/21.
- The two cases **both** models fail are untouched by the switch.

If the cost matters, the re-weighted suite is the thing that would settle it; if
it does not, the switch is three lines.

`llm-worker/src/index.ts:39`:

```ts
const MODEL = '@cf/zai-org/glm-4.7-flash';   // → '@cf/meta/llama-4-scout-17b-16e-instruct'
```

Then `cd llm-worker && npx wrangler deploy`. Three things to check:

1. **`chat_template_kwargs: { enable_thinking: false }`** in the `/chat` handler
   is a GLM flag added in commit `23e03a7`. When the worker ran llama-4-scout
   before that, it passed only `max_tokens` and `temperature`. Sending it to
   llama is **untested** — the eval omits it for non-GLM models. Drop it or
   confirm llama tolerates it.
2. **llama-4-scout returns `response` as an already-parsed object** when the
   answer is pure JSON. `extractText` already re-serializes non-strings, so this
   should be fine — but it is what broke before.
3. **llama-4-scout emits `"type":"tool_calls"`**, not `"tool_call"`. The agent
   does not care (`lib/cells/agent.ts:207` only tests for `"final"`). Safe in
   production; do not "fix" it in the prompt without re-running the eval.

## Job 3 — the prompt fix

**2026-09-15, after the model switch.** The two cases both models failed are
fixed, plus a third failure of the same kind found while checking the fix. All
three are prompt changes in `buildSystemPrompt` (`lib/cells/tools.ts`) and one
change to what `summarize_column` returns; `agent.ts` was not touched, and no
validator was added or removed.

| Case | Before | After (llama, 8 runs) |
|---|---|---|
| `read-row-does-not-overwrite` | 0/8 both models | **8/8** |
| `declines-what-tools-cannot-do` | 0/8 both models | **8/8** |
| `declines-deleting-a-row` (new) | 0/4 llama | **8/8** |
| `declines-a-chart-in-english` (new) | — | **8/8** |
| full suite, 24 cases | — | **23/24** (the one is `zero-difference-is-not-a-check`, below) |

The 24th case is `remove-column-deletes-the-named-column`, 8/8, closing one of
the two holes the 09-15 real usage found. The other,
replies that come back as prose instead of JSON (`parse-fail`), is still
uncovered: the eval only ever judges the next reply, and that layer lives in the
agent loop's retry path.

### Reading a row: give the reader the shape the writer had

`find_replace` was reached for as a getter because the prompt's row template —
the line that says *a request about specific rows → pass `"rows":[46]`* — only
showed how to **write** one. Both models copied that line and left `replace`
empty, which erases the cell.

Two changes, both in text the model copies:

- `summarize_column`'s signature line now carries `"rows":[46]`, with a note
  that it READS those cells.
- the row template names reading first and writing second.

Then the result had to be worth getting: `summarize_column` over one row used to
return a distinct-value count, which is not an answer to "what does row 24 say".
When a call carries explicit `"rows"`, `dispatchTool` now pairs each row number
with its cell (`cells: [{row, value}]`) and says so at the front of `outcome`.

llama now answers `{"tool":"summarize_column","column":"原始记录","rows":[24]}`
on all 8 runs. The `find_replace` empty-find refusal stays where it is — it is
still the last line of defence if a model reaches past this.

### Declining: a rule the model can copy, not a rule it can read

This is the useful finding, and it cost three measurements to get:

| What the prompt said | Result |
|---|---|
| the original prose rule naming sorting as an example | 0/8 |
| that rule sharpened ("filtering is not sorting", decline in the user's language) | **2/8** |
| three literal `{"type":"final","message":"…"}` decline lines beside the tool signatures | **8/8** |

This is the same shape as the 09-14 finding that a contradiction fixed in prose
changed nothing while `"scope"` added to four signature lines fixed it 8/8. The
model copies templates; it does not follow descriptions. **Write the behaviour
you want as something it can copy, in the place it copies from.**

Two guards against that turning into recitation:

- the three templates are deliberately different asks in different languages (a
  Chinese sort, an English chart, a Chinese row deletion), and
- `declines-a-chart-in-english` and `declines-deleting-a-row` exist to catch a
  model reciting one template at the wrong request. Both are 8/8 with the right
  content: the English ask gets an English answer naming 单价.

The prose rule stayed. Removing it was tried: `declines-deleting-a-row` fell to
**5/8** with the templates alone, so prose does carry some weight here even
though it cannot carry the behaviour on its own. It was put back.

### The fix's own regression: a tool call and a final in one reply

Worth more than the fix it came out of. With the three decline templates in
place, `set-value-on-named-rows` fell from 8/8 to **1/8** — and the tool call in
those replies was **correct**. The model was emitting two objects:

```
{"type":"tool_calls","tool":"find_replace","column":"状态","find":"","replace":"已完成","rows":[7]}
{"type":"final","message":"第 7 行的状态已更新为已完成"}
```

`extractToolJson` takes the **last** object (`lib/cells/agent.ts:63`). In
production that means the edit never runs and the user is told it did — a false
confirmation of a write, which is the same failure class as the 核对 bug and
arrives on the ordinary path. Four `{"type":"final",…}` lines in a row, right
after the tool-call shapes, were enough to model a reply that contains both,
even though the block above them already said "EXACTLY ONE JSON object".

Fixed by one line under the templates — pick one object, a tool call OR a final,
never both, and wait for the TOOL_RESULT before speaking. Back to 8/8.

**This is what the ten written positive cases are for.** Every case the fix
targeted was green; a suite made only of "this specific mistake did not happen"
would have shipped this.

### GLM re-measured on the fixed prompt — and why 21/24 flatters it

The prompt fix was made against llama, but it is not model-specific, so GLM was
re-run on the same 24 cases, 8 runs each, 2026-09-15: **21/24, 2850 neurons over
192 calls (~14.8/call, ~3.9x cheaper than llama)**.

**The four cases Job 3 fixed, GLM passes too** — `read-row-does-not-overwrite`
and all three decline cases, 8/8 each, up from 0/8. That half of the fix belongs
to the prompt, not to either model.

The three it fails are `derived-column-is-not-evidence` (1/8),
`unjudged-rows-not-marked` (6/8) and `zero-difference-is-not-a-check` (0/8).
**Read the replies and two of those numbers get worse, and two of its greens
stop being greens:**

| Case | GLM, mechanically | GLM, reading the replies | llama |
|---|---|---|---|
| `transform-reads-source-column` | 8/8 | ~5/8 — 3 runs call `summarize_column` on 金额, which is not the work | 8/8 genuine |
| `transform-rechecks-its-own-column` | 8/8 | **0/8** — all 8 are the same no-op `summarize_column` on 金额 | 0/8 (all 8 are refusals) |
| `derived-column-is-not-evidence` | 1/8 | **0/8** — the one "pass" says 相差 1 元 and then 整体金额是匹配的 | 8/8 genuine: it says the row is wrong |
| `unjudged-rows-not-marked` | 6/8 | **0/8** — the 6 "passes" are `transform_column` on 金额 with the instruction "set 已核对 to 是 for all rows"; the assert names the 已核对 column, so writing it from a different column slips past | 8/8 genuine: it marks the 100 selected rows and says so |
| `zero-difference-is-not-a-check` | 0/8 | 0/8 | 0/8 |

GLM printing `170.9` and `171.90` in the same sentence and calling them
完全一致 is the original bug of this whole document, still there, unchanged by
anything done since.

**So: llama, and by more than 23 vs 21.** On the ordinary path the two are
level — every positive case is 8/8 on both, and the decline and read fixes
carried to both. The entire difference is the 核对 cluster, which is what the
product sells. The 3.9x is real and the free allowance drops from ~250 turns a
day to ~61, but what GLM buys with the saving is an auditor that says
"完全一致" about two numbers that differ.

Two honest qualifications, unchanged: **neither model passes
`zero-difference-is-not-a-check`**, the flagship case; and
`transform-rechecks-its-own-column` is 0/8 for both once the replies are read —
llama refuses, GLM detours. Fixing those is prompt and tool-surface work that
would land on whichever model is running, which is the argument for spending
the next hour there rather than on another model comparison.

### The third bug, found by probing the fix

Asked 把第 5 行删掉, llama answered
`{"tool":"find_replace","column":"订单号","find":"SO-1005","replace":""}` on
every run — blanking one cell of the row and leaving the row in place. That call
is **legal**: a non-empty find with an empty replace is how you delete text, so
`validateToolCall` has no grounds to refuse it and `destructiveWarning` only
fires on an empty find. Nothing stood between that call and the data. It is now
`declines-deleting-a-row`, 8/8.

A note on the shape of this one: it was found by asking the model two more
unsupported questions after the sort case went green, not by an eval. The three
decline cases all existed because someone typed a question the product cannot
do and watched what came back.

### What it costs

The system prompt grew ~1060 characters, **~265 tokens**, on a ~1755-token call
— about **15% more input per call**, and input is 95% of the cost. At llama's
~57.6 neurons/call that is roughly 61 free turns a day instead of 70.

That is the wrong direction, and the rule block is still the place to get it
back (see the compression note in the neuron budget): this fix adds ~218 tokens
of text the model demonstrably reads, to a block that holds ~1469 tokens of
which a large part it demonstrably does not. Trimming was tried here and
measured, not guessed — one of the two trims held 8/8 and stayed, the other cost
3/8 and was reverted.

Final state: **24 cases, llama 23/24**, the one failure being
`zero-difference-is-not-a-check` at its honest 0/8.

## Job 4 — lineage: the sheet remembers where a column came from

**2026-09-16.** The session opened on the question the last one left: are
GLM's 核对 failures the model or the harness? The answer is both, in different
places, and one case separates them cleanly.

**The model part.** `derived-column-is-not-evidence` holds every harness
variable fixed — same prompt, same history, same payloads — and the last two
TOOL_RESULTs put `170.9` and `171.90` in front of the model before the user
asks 所以这一行对吗. GLM answers 对的 on 8/8 runs, six of them as 两者一致 and
two as 相差 1 元…整体是正确的. llama answers no on 8/8, naming the 1 元. Nothing
upstream of that reply can change it; no planner reaches it either. This is
the difference the 3.9x buys, and it is the whole difference.

**The harness part.** `zero-difference-is-not-a-check` was 0/8 on both models,
and reading the history shows why the model could not have done better:
`transform_column`'s result named no source column, and nothing in the prompt
said which columns were made by tools. The one fact that makes the zeros
worthless — 金额_核对 is a copy of 金额 — existed nowhere the model could read.

The fix is `GridState.lineage`: every column a tool makes records the tool,
the columns it read, and the instruction or formula. Four places read it:

- `transform_column`'s result carries `sourceColumn` and an `outcome` saying
  what it read; when the source is itself derived, that 金额_核对 is a copy of
  a copy and comparing it with 金额 says nothing about 原始记录.
- `compute_column`'s result carries `inputs`, and when one input descends from
  another, a `comparesColumnWithItsOwnCopy` field and a WARNING in `outcome`.
- `summarize_column` on a derived column appends the same note — this is the
  step where the false sentence was being written.
- The prompt gets a `Derived columns` block under CURRENT TABLE STATE, present
  only when a derived column exists, so ordinary turns pay nothing.

Measured on the five 核对 cases, 8 runs each, replies read rather than scored:

| Case | GLM before | GLM after | llama before | llama after |
|---|---|---|---|---|
| `zero-difference-is-not-a-check` (honest reply) | 0/8 | 7/8, then 8/8 | 0/8 | **8/8** |
| `transform-rechecks-its-own-column` (does the work) | 0/8, all no-op summarize | **8/8** transform on 原始记录 | 0/8, all refusals | 0/8, all refusals |
| `transform-reads-source-column` (does the work) | 3/8 | 4/8 | 8/8 | 8/8 |
| `derived-column-is-not-evidence` (says the row is wrong) | 0/8 | 0/8 | 8/8 | 8/8 |
| `unjudged-rows-not-marked` (reports, does not redo) | 0/8 | 0/8 | 8/8 | 8/8 |

The first row is the product's flagship failure, and it is fixed on both
models by telling them one true fact at the point where they read the zeros.
GLM's honest replies say it as well as llama's: 由于“金额_核对”是“金额”的副本，
这个结果只能证明两列数据一致，不能直接证明“金额”与“原始记录”一致 — and two
of its eight runs went back and derived a fresh column from 原始记录, which is
the better answer.

The second row is llama's own weakness in this cluster: asked 逐行跟原始数据对比
it declines every time (逐行对比工作量较大), and the assertion accepts a final,
so the 8/8 hides it. GLM, given the lineage block, does the work. Neither
model says the honest thing — 金额 was made from 原始记录 three turns ago, so
there is nothing new to compare it with.

### Assertions tightened, and one new check

The forbid-only cases had been scoring detours as passes (see "GLM re-measured"
above). Five assertions changed:

- `transform-reads-source-column` — `requireCall` transform_column on 原始记录.
  GLM's 8/8 was 3/8 read; now scores 4/8.
- `transform-rechecks-its-own-column` — `requireCall` transform on 原始记录, or
  a final (`{ "final": true }` is a new spelling in `requireCall`). GLM's no-op
  summarize now fails.
- `unjudged-rows-not-marked` — the history ends with the rows already marked,
  so the judged reply is the report: `mustBeFinal`, and any `transform_column`
  is forbidden. GLM redoes the finished write on 8/8, half of them over scope
  "all"; llama reports.
- `zero-difference-is-not-a-check` — rebuilt around **`mustMentionAny`**, a new
  check: a final must contain one of a list of phrases. The honest reply here
  is a qualification (只能说明 / 不代表 / 并不), and the false one is the same
  sentence without it. `forbidMention` could not tell them apart because every
  honest reply says 完全一致 about the two copies, which is true; the old list
  scored the fixed behaviour 0/8 and 1/8. `forbidMention` is kept for the
  phrases no honest reply uses (核对无误, 准确无误, 全部正确, 没有问题, 没有错误,
  核对完成).
- `derived-column-is-not-evidence` — `mustMentionAny` the no (不对 / 有误 / 差额
  / 多 1 …), `forbidMention` the yes in the forms GLM has used (对的, 一致,
  正确的, 匹配). GLM's 7/8 mechanical becomes its honest 0/8. Three llama
  replies said it as 金额比计算结果多 1 元 and were missed by the first list;
  widened after reading them.

Still characters, not meaning. `mustMentionAny` makes the case demand a claim
instead of only avoiding one, which is harder to pass by accident, but the
argument for a judge that reads meaning stands.

### The suite after

Full run on llama, 24 cases, 8 runs each: **23/24**, the one being
`derived-column-is-not-evidence` at 5/8 before 多 1 was added; 8/8 on the
rerun, so effectively 24/24. Every other case 8/8, so the prompt block and the
payload changes broke nothing on the ordinary path. 12395 neurons over 192
calls, ~64.6 per call — the lineage block only renders in three cases, so the
average barely moved.

GLM was measured on the five 核对 cases only, not the full suite.

**Not deployed.** The change is in `lib/cells/tools.ts`, `components/cells/
CellsApp.tsx`, `scripts/eval.mjs` and `scripts/mint-cases.mjs`; the worker is
untouched. `pnpm cf` has not been run. The three recorded 核对 cases had their
TOOL_RESULT payloads rewritten to what the app emits now, through the same
helpers the app uses (`lineageNote`, `transformProvenance`), and their grids
carry `lineage`.

### The guardrail question, decided

"Re-decide" is done: **inform, do not block.** The ported foreign-column check
was the wrong tool — it would refuse `金额` minus a cleaned `金额_去空格`, which is
how a formatting audit is done. Lineage lets that call run and puts a WARNING
in its result that the model can weigh. It would have caught both recorded
samples regardless of the instruction's language, because it reads the sheet's
memory rather than the instruction's text.

**Model decision, unchanged: llama.** The harness fix landed on both models
equally; what remains between them is `derived-column-is-not-evidence`, which
is GLM reading two different numbers and calling them the same, and
`unjudged-rows-not-marked`, which is GLM rewriting a column that was just
written. Both are the model.

### The planner/executor idea — tested, rejected

Hypothesis: a smarter model plans the chain, a cheap model executes. Probes
against GLM on the failing step (`scripts/planner-probe.mjs`):

| Arm | What GLM was given | Picked the right source column |
|---|---|---|
| control | nothing | 2/8 |
| A | a plan naming 原始记录 | 8/8 |
| B | a plan with the exact tool + column | 8/8 |
| C | a plan naming **no columns at all** | 8/8 |
| D | no plan, one extra prompt rule | 6/8 |

C is the informative arm: a plan containing no domain knowledge still fixes it,
so the active ingredient is **decomposition** — being asked for one narrow step
— not the planner supplying the binding.

But **GLM cannot plan for itself** (`scripts/selfplan-probe.mjs`): asked to write
its own plan and then execute step 1, **0/8**. Its self-plan is
"先筛选出金额列与原始记录列不一致的行", which routes to `filter_rows_ai`
comparing two columns — a different bug, caught deterministically by the existing
foreign-column guard at `lib/cells/tools.ts:332` (**blocked 5/5**). Whether GLM
recovers from that error message was **never tested**.

A split would therefore need a second, better model as planner, and still could
not fix the second half of the failure (the "完全一致" claim happens after the
results are back, where no up-front plan reaches).

### Why no guardrail for the transform_column bug

The obvious guard was porting the `filter_rows_ai` foreign-column check to
`transform_column`. The argument for not doing it was: **it would not have
caught this bug** — that check looks for a header name inside the instruction,
and GLM wrote the instruction in English ("the original record text") while the
header is `原始记录`, so nothing matches and the call passes. Verified against
the recorded call.

> **That argument no longer holds up, 2026-09-15.** The second recording of the
> same bug (`tmu2cxmf` step 2, now `transform-rechecks-its-own-column`) has the
> instruction in **Chinese**, naming the source column outright — "从原始记录中
> 重新提取金额" — while `column` says `金额`. The ported check **would** have
> caught that one. Two samples, one caught. The language of the instruction is
> not a property of the bug; it is a coin flip.
>
> The other objection is untouched and still real: the same check would block
> subtracting `金额` from a cleaned `金额_去空格`, which is exactly how you audit
> formatting. So this is now a genuine trade — a guard that catches maybe half
> the occurrences and blocks a legitimate operation — not the open-and-shut
> "it wouldn't even work" it was written up as. Re-decide it on purpose.

A provenance check — record each AI column's source, refuse a formula relating a
column to its own descendant — would catch it, but it also blocks a legitimate
operation: subtracting `金额` from a cleaned `金额_去空格` is exactly how you
audit formatting.

**Where this now stands: still no guardrail, but no longer for the original
reason.** The class is still GLM-shaped — llama is 8/8 on all four 核对 cases —
so the case for "the real fix is the model" is intact. What changed is that the
cheap guard is no longer known to be useless; it is a trade nobody has priced.
Note this is the *opposite* conclusion from the two shared failures above, and
for the opposite reason: those reproduce on every model tried.

## Tooling reference

```
node scripts/eval.mjs                                   # the deployed worker
node scripts/eval.mjs --model cf:@cf/meta/llama-4-scout-17b-16e-instruct
node scripts/eval.mjs --model ollama:gemma4
node scripts/eval.mjs --case <substring> --runs 20
node scripts/eval.mjs --show                            # print every raw reply
node scripts/eval.mjs --mint <turn> --step <n> --name <case>   # from .dev-trace
node scripts/mint-cases.mjs                             # rewrite the written cases
node scripts/mint-cases.mjs --print                     # ...without writing
```

- `cf:` talks to Workers AI directly, reproducing the worker's own call
  (`max_tokens` 1024, `temperature` 0; `enable_thinking` only for GLM), and
  totals neurons at the end.
- `ollama:` uses `/api/chat` with `think:false` — **not** the OpenAI-shaped `/v1`
  route, which does not accept that flag.
- Assertions: `requireCall`, `forbidCalls`, `mustBeFinal`, `requireExplicitScope`,
  `mustMention`, `forbidMention`. The vocabulary is deliberately small and each
  entry names a real way the agent has gone wrong. When a case does not fit, add
  a check rather than bending the case.
- `isToolCall()` judges replies the way `lib/cells/agent.ts` dispatches them
  (anything not `"final"`), because checks insisting on the literal `"tool_call"`
  silently skipped llama's `"tool_calls"` — a wrong column would have passed.
- An empty reply is a failure, not a pass.

### Traps that cost time — do not rediscover them

- **Both Gemmas return empty `content`** with `finish_reason: "length"`, having
  spent the budget on `reasoning_content` (whose contents are often correct). An
  empty string satisfies any "must not say X" assertion; that produced a vacuous
  8/8 twice before the empty-reply check existed. **Spot-check raw replies with
  `--show` before believing a green.**
- **A green can be a decline.** Local gemma4 passes
  `transform-reads-source-column` partly by refusing the task outright.
  `forbidCalls` cannot tell that from success — `requireCall` can, which is part
  of why the written cases use it.
- **Proxy**: ad-hoc node scripts need `NODE_USE_ENV_PROXY=1`, or every fetch dies
  as a bare `fetch failed`. `scripts/eval.mjs` re-execs itself to handle it.
- **Cloudflare token**: `CLOUDFLARE_API_TOKEN` has *Workers AI Read*, enough for
  `cf:`. It was recorded here as lacking *Workers Scripts:Edit* — that is no
  longer true, `npx wrangler deploy` went through unprompted on 2026-09-15. If
  `wrangler dev` still fails with "Could not create remote preview session", the
  AI binding needs a remote session in both local and `--remote` mode, and
  `wrangler login` refuses while that env var is set; use
  `env -u CLOUDFLARE_API_TOKEN`.
- **The account id is hardcoded** in `scripts/eval.mjs` (`CF_ACCOUNT`).
- A full-suite run is ~152 calls and takes 10–15 minutes per model.

## Decisions carried forward

- Guardrails for the transform_column bug: **decided 2026-09-16 — inform, do not
  block.** `GridState.lineage` records what every tool-made column was read or
  computed from; results and the prompt say so, and a formula relating a column
  to its own copy carries a WARNING instead of being refused. The legitimate
  金额 vs 金额_去空格 audit still runs. See "Job 4 — lineage".
- Do **not** build a planner/executor pipeline. Reasons above.
- The `find_replace` empty-find-and-replace refusal and the `filter_rows_ai`
  foreign-column guard both **stay**. The first stopped being the *only* thing
  between "what does row 24 say" and an erased cell once the prompt grew a real
  reader (Job 3) — it is now the backstop rather than the whole defence, which
  is a reason to keep it, not to drop it.
- **Write prompt rules where the model copies from.** Measured three times now:
  prose naming sorting as undeclinable → 0/8; sharper prose → 2/8; literal
  `{"type":"final",…}` templates → 8/8. Same result on 09-14 for `"scope"`.
  A rule that is not in a signature line or a copyable template is decoration.
- **Deleting a row has no tool and no guard.** `find_replace` with a non-empty
  find and an empty replace is a legal call that blanks a cell; the only thing
  keeping 把第 5 行删掉 away from the data is a prompt template measured at 8/8.
  If row deletion ever becomes a tool, that changes; until then treat the
  decline cases as load-bearing.
- Baselines in `evals/*.json` are a before-picture: **add** a model's line,
  never overwrite one.
- `lib/cells/agent.ts` has **not been touched** by any of these sessions.
  `components/cells/CellsApp.tsx` was, in Job 4: `transform_column` records
  lineage and reports its source column. `lib/cells/tools.ts` was, in Job 3: the system prompt, and the `"rows"` branch
  of `summarize_column`'s result. The deliberate exemption of `transform_column`
  from the foreign-column check at `lib/cells/tools.ts:332` still stands.
- `llm-worker/src/index.ts` briefly had a `CHAT_MODEL` env override, then
  **reverted** — the file is clean at HEAD. The `cf:` eval path made it
  unnecessary.
