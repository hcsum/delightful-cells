# Handover: the eval suite exists — what it says, and what it still can't say

Written 2026-09-14/15 across two sessions. The first started as "look at the
latest trace", ended in a model question it could not answer, and wrote Job 1.
This is the same document with Job 1 done. Every number was measured, not
estimated.

- **Job 1 (done, minus one piece): an eval suite that is not one model's error
  book.** 21 cases, 14 of them written rather than recorded, covering the
  ordinary path as well as the known bugs. What is still missing is
  **weighting** — see "Real usage: 6 turns in".
- **Job 2 (done 2026-09-15): the model is now
  `@cf/meta/llama-4-scout-17b-16e-instruct`.** Deployed, verified, and costing
  ~4.2x per call. See "Job 2 — done" for what was checked.

**Three findings worth reading before anything else:**

1. **Two cases fail 0/8 on both models**, in the same way. Those are not a
   model's mistakes — they are the prompt and the tool surface, and no model
   swap touches them. → "The two cases both models fail".
2. **The suite cannot judge the last sentence.** Its two text assertions match
   characters, not meaning, and a model saying the same false thing in other
   words — or in English — passes. A green there is not evidence until you have
   read the replies. → "The suite's own ceiling".
3. **One argument in this document was overturned** by a second recording of the
   original bug: the reason given for not guarding `transform_column` does not
   hold. → "Why no guardrail for the transform_column bug".

## The bug that started this

A real run (`tmu1aprvrpjmmkmmx`, in `.dev-trace/2026-09-14.jsonl`) answered
"根据原始记录判断一下金额对不对" with "154 行全部正确". That was false.

The chain broke at step 2:

```json
{"tool":"transform_column","column":"金额",
 "instruction":"Extract the numeric amount from the original record text…",
 "newColumnName":"金额_提取"}
```

`transform_column` only sees the cell of the column it is given. `column` was
the *target* (`金额`), not the *source* (`原始记录`), so it read the already
formatted `171.90` and "extracted" `171.9` back out. Then
`compute_column [金额] - [金额_提取]` subtracted a column from its own AI copy
and returned 0 on all 154 rows, which the model reported as proof.

Row 24 disproves it: `原始记录` is `拼车88+82.9=170.9`, `金额` is `171.90`, off
by 1. In a later turn the model printed both numbers itself and still called
them 完全一致.

This failure class matters more than a crash: the product's selling point is
核对, and an audit that confidently returns "all correct" fails invisibly.

21 cases in `evals/`, of two kinds.

**7 recorded** — cut out of `.dev-trace` with `--mint`, each one a real failure
that really happened. They keep their original `why` and their GLM baseline.

**14 written** — generated by `scripts/mint-cases.mjs` from invented sheets.
These are the ones that make the suite something other than a catalogue of
GLM's mistakes. Ten of them assert that the **ordinary path still works**,
which nothing in the old suite did: a suite made only of "this specific mistake
did not happen" can prove a regression was fixed and cannot notice a model that

### How the written cases are built

`scripts/mint-cases.mjs` holds a recipe per case — the sheet, the user's
message, the steps that already ran, and the assertion — and writes the JSON in
`evals/`. **Edit the recipe, not the JSON**; regeneration overwrites it.

The reason it is a generator and not hand-typed JSON is the multi-step cases.
Their history contains TOOL_RESULT payloads, and those are not free text:
`dispatchTool` words each `outcome` sentence deliberately, and half of what the
recorded cases catch is a model misreading one. A plausible-looking but subtly
wrong payload tests the model against something production never emits. So
every TOOL_RESULT in a written case comes out of the **real `dispatchTool`**,
and every assistant turn is the **real `validateToolCall`** output — the same
JSON `lib/cells/agent.ts` would have put in the history. Re-run the generator
after changing a tool's wording and the cases follow.

Two tools cannot be replayed this way: `transform_column` and `filter_rows_ai`
are executed by the UI layer and `dispatchTool` throws for both. No written
case needs one today. A case that does needs a real trace, or a payload copied
out of one — `evals/scope-stated-not-guessed.json` has both shapes.

The sheets are invented (订单表 120 rows, 反馈表 80 rows, plus a rebuilt 明细表
for the two cases that need 原始记录). Deliberately not the one spreadsheet the
recorded cases came from: a suite built on a single sheet measures how a model
does on that sheet.

### New tooling this session

- `scripts/build-tools.mjs` — compiles `lib/cells/tools.ts` once and hands back
  the real module. `eval.mjs` and `mint-cases.mjs` both use it.
- `requireCall` in `eval.mjs`'s `CHECKS` — the positive assertion. Lists the
  calls that answer the request; several alternatives are allowed where more
  than one genuinely does. It shares its matcher with `forbidCalls` so "do X"
  and "don't do X" cannot drift apart.
- `node scripts/eval.mjs --show` — prints every raw reply as it arrives. Use it
  before believing a green; see the traps below for why.

- `zero-difference-is-not-a-check` — llama scored a clean **8/8 while saying the

**GLM passes every one of the ten written positive cases.** That is worth

own output back as evidence.

### The two cases both models fail

Neither is a model problem, and neither was visible while the suite was made of
GLM's mistakes.

**`read-row-does-not-overwrite`** — asked "第 24 行的原始记录写的是什么？", both
models emit the identical call, on every single run:

```json
{"tool":"find_replace","column":"原始记录","find":"","replace":"","rows":[24]}
```

`find_replace` is the only tool whose example shows `"rows"`, so it gets reached
for as a getter — and it writes. With both fields empty it erases the cell the
user asked about. `validateToolCall` refuses that exact shape (the check added
at `lib/cells/tools.ts`, empty find + empty replace), which is the only reason
the data survives. **That guard is load-bearing on both models**, not a
belt-and-braces check for one; it should not be simplified away. What the user
sees today is a stall and a retry, not an answer.

**`declines-what-tools-cannot-do`** — asked to sort by 单价, neither model
declines. GLM invents a tool that does not exist
(`{"tool":"sort_rows","column":"单价","direction":"desc"}`) or reaches for
`summarize_column`; llama calls `filter_rows`, every run. The prompt names
sorting as its own example of what to decline, and the rule does not take. The
invented tool is caught by the validator; **a legal `filter_rows` standing in
for a sort is not caught by anything**.

Both are prompt / tool-surface work, and both are now pinned by a case, so a
fix can be shown to work. Neither was touched this session — that is a call for
whoever picks it up, not something to slip into an eval change.

### The suite's own ceiling: it cannot judge the last sentence

Every assertion here is mechanical except two — `forbidMention` and
`mustMention` — and those match **characters, not meaning**. That is fine for
"did it tell the user 54 rows went unjudged" (a number either appears or it does
not). It is not fine for the failure this product lives or dies on: *did the
model claim the data is verified when nothing was verified.*

The measurement above is what that costs. `zero-difference-is-not-a-check`
passed llama 8/8 on its first run while llama was saying the false thing in
different words. Widening the list fixed that model, that day, in that language
— and Cells is bilingual (`lib/cells/i18n.ts`: `en | zh`, and 4 of the 16
recorded turns were asked in English), so the same claim in English walks
through a Chinese phrase list untouched.

**So: a green on a `forbidMention` case is not evidence unless you have read the
replies.** `--show` prints them. This applies to
`derived-column-is-not-evidence` too, which forbids the single phrase 完全一致.

Judging this properly needs something that reads meaning — an LLM judge on the
final message. That was considered and **deliberately not built**: it puts a
model-shaped, non-deterministic judge into a suite whose every other assertion
is a string comparison, and it wants its own validation set before anyone could
trust it. The 16 replies collected above (8 GLM, all false; 8 llama, 5 false and
3 accurate) are a ready-made validation set for whoever picks this up. Until
then the limit is written into each affected case's `why`.

### One behaviour observed, deliberately not asserted

GLM will not do arithmetic while any tool is left uncalled. Given
`filter_rows` → "30 of 120 matched", it calls `summarize_column` instead of
dividing (8/8). Given `summarize_column` first, it calls `filter_rows` (4/4).
Given both, it answers "退款率 25%" every time. It gets there; it costs a round
trip. `rate-reported-as-a-percentage` therefore hands it both results and
asserts only the division — a one-step version would score 0/8 while measuring
something else entirely.

## Real usage: 6 turns in, what it bought

`.dev-trace/2026-09-15.jsonl` — 6 turns of ordinary use, collected after the
suite was written.

**Not enough to weight anything.** All 6 sit on one line of work — extract the
amount, 核对 it, delete the leftover column — the same line as 09-13 and 09-14.
Half the tool surface never came up: no filter, no count, no rate, no semantic
filter, no setting a value on named rows, nothing the tools cannot do. Weighting
needs *different work*, not more turns of the same. Best next step: a sheet that
is not this expense table — orders, a contact list, anything — used normally for
20 minutes, without aiming at 核对.

**But it paid for itself three times over:**

1. **The core bug reproduced, in its cleanest form yet** (`tmu2cxmf20pmtdc0p`),
   and it is now two cases. What makes this recording better than the original:
   the user had just asked for 金额 to be built *from* 原始记录, and the model
   built it correctly. So when the next request was 逐行跟原始数据对比, the
   column it re-extracted from was **its own earlier output** — `金额_核对` is a
   copy of a copy — and `[金额] - [金额_核对]` was 0 on all 153 rows, reported as
   "153行数据金额一致，差异均为0，核对无误". Every step succeeded. Nothing
   errored. The answer was false.
2. **It overturned an argument in this document** — see the guardrail section
   below.
3. **It found two holes in the suite.** `remove_column` ("把差异列删了") has no
   case at all; it was missed when the scenarios were picked off the tool
   surface. And 3 of the 6 turns came back as prose rather than JSON, logged as
   `parse-fail` — the agent loop handles it, but the eval only ever judges "the
   next reply", so nothing in `evals/` covers that layer.

**The sampling rule still stands**, and is the reason turn 1 above is worth as
much as the failures: collect turns regardless of whether the model got them
right, and mint from both.

Minting only from failures is how the old suite became an error book. The turns
GLM handles correctly are the most valuable ones to freeze — they are the pass
mark that catches a regression when the model changes.

With a wider sample in hand: re-weight (add cases where real use is dense, drop
or merge where it is thin), re-run both models, and Job 2 answers itself.

### The evidence it was decided on

The state of the evidence: **llama-4-scout passes everything GLM passes, plus
four of the five cases GLM fails on its own, at 4.2x the cost.** No case
separates them the other way. GLM's free allowance of 10,000 neurons/day is
roughly 730 GLM turns or 175 llama turns at this session's measured rates, and
points are denominated in neurons — which is where the 4x actually bites.

Three caveats on that sentence, none of them small:

- It has *not* been shown that llama is better in general. It is better on these
  21 cases, and the 21 are still unweighted.
- Two of llama's wins are softer than the score
  (`transform-rechecks-its-own-column`, where all 8 of its passes are refusals;
  `zero-difference-is-not-a-check`, where 5 of 8 replies are the same false
  claim GLM makes). Read those notes before treating 18/21 as 18/21.
- The two cases **both** models fail are untouched by the switch.

If the cost matters, the re-weighted suite is the thing that would settle it; if
it does not, the switch is three lines.

`llm-worker/src/index.ts:39`:

```ts
const MODEL = '@cf/zai-org/glm-4.7-flash';   // → '@cf/meta/llama-4-scout-17b-16e-instruct'
```

Then `cd llm-worker && npx wrangler deploy`. Three things to check:

1. **`chat_template_kwargs: { enable_thinking: false }`** in the `/chat` handler
   is a GLM flag added in commit `23e03a7`. When the worker ran llama-4-scout
   before that, it passed only `max_tokens` and `temperature`. Sending it to
   llama is **untested** — the eval omits it for non-GLM models. Drop it or
   confirm llama tolerates it.
2. **llama-4-scout returns `response` as an already-parsed object** when the
   answer is pure JSON. `extractText` already re-serializes non-strings, so this
   should be fine — but it is what broke before.
3. **llama-4-scout emits `"type":"tool_calls"`**, not `"tool_call"`. The agent
   does not care (`lib/cells/agent.ts:207` only tests for `"final"`). Safe in
   production; do not "fix" it in the prompt without re-running the eval.

### The planner/executor idea — tested, rejected

Hypothesis: a smarter model plans the chain, a cheap model executes. Probes
against GLM on the failing step (`scripts/planner-probe.mjs`):

| Arm | What GLM was given | Picked the right source column |
|---|---|---|
| control | nothing | 2/8 |
| A | a plan naming 原始记录 | 8/8 |
| B | a plan with the exact tool + column | 8/8 |
| C | a plan naming **no columns at all** | 8/8 |
| D | no plan, one extra prompt rule | 6/8 |

C is the informative arm: a plan containing no domain knowledge still fixes it,
so the active ingredient is **decomposition** — being asked for one narrow step
— not the planner supplying the binding.

But **GLM cannot plan for itself** (`scripts/selfplan-probe.mjs`): asked to write
its own plan and then execute step 1, **0/8**. Its self-plan is
"先筛选出金额列与原始记录列不一致的行", which routes to `filter_rows_ai`
comparing two columns — a different bug, caught deterministically by the existing
foreign-column guard at `lib/cells/tools.ts:332` (**blocked 5/5**). Whether GLM
recovers from that error message was **never tested**.

A split would therefore need a second, better model as planner, and still could
not fix the second half of the failure (the "完全一致" claim happens after the
results are back, where no up-front plan reaches).

### Why no guardrail for the transform_column bug

The obvious guard was porting the `filter_rows_ai` foreign-column check to
`transform_column`. The argument for not doing it was: **it would not have
caught this bug** — that check looks for a header name inside the instruction,
and GLM wrote the instruction in English ("the original record text") while the
header is `原始记录`, so nothing matches and the call passes. Verified against
the recorded call.

> **That argument no longer holds up, 2026-09-15.** The second recording of the
> same bug (`tmu2cxmf` step 2, now `transform-rechecks-its-own-column`) has the
> instruction in **Chinese**, naming the source column outright — "从原始记录中
> 重新提取金额" — while `column` says `金额`. The ported check **would** have
> caught that one. Two samples, one caught. The language of the instruction is
> not a property of the bug; it is a coin flip.
>
> The other objection is untouched and still real: the same check would block
> subtracting `金额` from a cleaned `金额_去空格`, which is exactly how you audit
> formatting. So this is now a genuine trade — a guard that catches maybe half
> the occurrences and blocks a legitimate operation — not the open-and-shut
> "it wouldn't even work" it was written up as. Re-decide it on purpose.

A provenance check — record each AI column's source, refuse a formula relating a
column to its own descendant — would catch it, but it also blocks a legitimate
operation: subtracting `金额` from a cleaned `金额_去空格` is exactly how you
audit formatting.

**Where this now stands: still no guardrail, but no longer for the original
reason.** The class is still GLM-shaped — llama is 8/8 on all four 核对 cases —
so the case for "the real fix is the model" is intact. What changed is that the
cheap guard is no longer known to be useless; it is a trade nobody has priced.
Note this is the *opposite* conclusion from the two shared failures above, and
for the opposite reason: those reproduce on every model tried.

## Tooling reference

```
node scripts/eval.mjs                                   # the deployed worker
node scripts/eval.mjs --model cf:@cf/meta/llama-4-scout-17b-16e-instruct
node scripts/eval.mjs --model ollama:gemma4
node scripts/eval.mjs --case <substring> --runs 20
node scripts/eval.mjs --show                            # print every raw reply
node scripts/eval.mjs --mint <turn> --step <n> --name <case>   # from .dev-trace
node scripts/mint-cases.mjs                             # rewrite the written cases
node scripts/mint-cases.mjs --print                     # ...without writing
```

- `cf:` talks to Workers AI directly, reproducing the worker's own call
  (`max_tokens` 1024, `temperature` 0; `enable_thinking` only for GLM), and
  totals neurons at the end.
- `ollama:` uses `/api/chat` with `think:false` — **not** the OpenAI-shaped `/v1`
  route, which does not accept that flag.
- Assertions: `requireCall`, `forbidCalls`, `mustBeFinal`, `requireExplicitScope`,
  `mustMention`, `forbidMention`. The vocabulary is deliberately small and each
  entry names a real way the agent has gone wrong. When a case does not fit, add
  a check rather than bending the case.
- `isToolCall()` judges replies the way `lib/cells/agent.ts` dispatches them
  (anything not `"final"`), because checks insisting on the literal `"tool_call"`
  silently skipped llama's `"tool_calls"` — a wrong column would have passed.
- An empty reply is a failure, not a pass.

### Traps that cost time — do not rediscover them

- **Both Gemmas return empty `content`** with `finish_reason: "length"`, having
  spent the budget on `reasoning_content` (whose contents are often correct). An
  empty string satisfies any "must not say X" assertion; that produced a vacuous
  8/8 twice before the empty-reply check existed. **Spot-check raw replies with
  `--show` before believing a green.**
- **A green can be a decline.** Local gemma4 passes
  `transform-reads-source-column` partly by refusing the task outright.
  `forbidCalls` cannot tell that from success — `requireCall` can, which is part
  of why the written cases use it.
- **Proxy**: ad-hoc node scripts need `NODE_USE_ENV_PROXY=1`, or every fetch dies
  as a bare `fetch failed`. `scripts/eval.mjs` re-execs itself to handle it.
- **Cloudflare token**: `CLOUDFLARE_API_TOKEN` has *Workers AI Read*, enough for
  `cf:`. It was recorded here as lacking *Workers Scripts:Edit* — that is no
  longer true, `npx wrangler deploy` went through unprompted on 2026-09-15. If
  `wrangler dev` still fails with "Could not create remote preview session", the
  AI binding needs a remote session in both local and `--remote` mode, and
  `wrangler login` refuses while that env var is set; use
